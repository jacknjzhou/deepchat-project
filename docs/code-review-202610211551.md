## 🔴 High（4 项，均已读码核实）

### H1. 续传把失败的 run 标成 completed

`src/main/digital-employee/remoteRunner.ts:250-255`

断线续传（resumeWithRetry）成功后无条件 `finishSuccess(input, state, inFlightRunId, flusher, 'completed', null)`，不读续传期间 `applyFrame` 记录的 `terminalEvent` / `state.failureCode`。断连期间服务端已失败时，续传重放出的 `run.failed` / `run.cancelled` 帧也会被标 sent + completed，消息永久丢失失败语义。

**修复**：续传成功路径复用主路径的终态分发（failed → failRun，cancelled → 'cancelled'），并补查 result。

### H2. 旧 run 游标污染新 run

`src/main/digital-employee/remoteRunner.ts:218`（`let lastEventId = binding.lastEventId`）

新 run 首帧前断连时，resume 用新 runId + 旧游标；若服务端 sequence 按 job 计数，则跳过全部事件 → 3 次重试全败 → hybrid 会话被 `shouldFallBackToLocal` 静默解绑降级。

**修复**：`streamRun` 抛错且 run 为本轮新建时，resume 用 `lastEventId = null`（重放幂等安全）。

### H3. 技能下载 fetch 无超时

`src/main/digital-employee/skillSync.ts:158-160`

`installOne` 的 fetch 未加 `AbortSignal.timeout`（对比 `knowledgeClient` 全部请求 10s 超时），而 provision 链在会话建立前 await 它——服务端挂起即永久卡死新会话建立。

**修复**：加 `AbortSignal.timeout(REQUEST_TIMEOUT_MS)` + 失败重试上限。

### H4. rebuild 知识同步竞态

`src/main/app/composition.ts:3768-3770`

`rebuildKnowledgeSync` 先 `stop()` 旧 scheduler 再新建实例，但 stop 不等待旧轮 in-flight 完成，新实例闸门不感知旧轮，两轮 `syncEmployee` 可并发写同一 `knowledgeSyncState`（read-modify-write 无锁互相覆盖）。

**修复**：`stop()` 返回并 join in-flight promise，或模块级 per-employee 互斥。

## 🟡 Medium（11 项）

1. **zip-bomb** — `skillSync.ts:102-131` `ensureSkillFrontmatter` 用 `fflate unzipSync` 整包解压到内存重打包，仅限压缩包 ≤64MB，解压后累计大小无上限；server 可控字节，64MB 恶意 zip 可膨胀至 GB 级内存 DoS。参照 `src/main/skill/archive.ts:211-214` 的 `maxExtractedBytes` 限额。
2. **换址重发积压** — `backflowRetry.ts:133-146` + `composition.ts:3549-3560`：队列行不记录 baseUrl；保存新 baseUrl → onConfigurationChanged → rebuild → `kick()` 立即 drain，把旧地址攒的对话正文 POST 到新服务器（隐私风险）。修复：行内记录 baseUrl 摘要、mismatch 即 drop，或 save 检测换址时清队（带用户确认）。
3. **SSE CRLF 跨 chunk 断裂** — `sseParser.ts:96` 只对新增 chunk 做 `\r\n`→`\n` 归一化，`\r` 在上一 chunk 尾、`\n` 在下一 chunk 头时不被替换 → 终止帧 `KNOWN_EVENT_NAMES` 失配被当未知事件丢弃，挂满超时。修复：拼接后统一替换或暂存尾 `\r`。
4. **续传成功路径不查 result** — awaiting_input 追问提示只在首轮 `/result` 拉取（remoteRunner.ts:276 注释自述），首轮之后的断连续传会丢失追问提示。
5. **getResult zod strict 零容忍** — `remoteClient.ts:253-255`：服务端可选字段漂移即 ZodError，被 execute 当传输错误判死整轮（流其实已成功）。建议 safeParse + 降级保留正文。
6. **120s 硬性流超时** — `remoteClient.ts:195,229` `AbortSignal.timeout(STREAM_IDLE_TIMEOUT_MS)` 是总超时而非空闲超时，>2min 的 run 被掐断后靠 resume 续命，与 H2 叠加。应改 AbortController + 每 chunk 重置的空闲定时器。
7. **cancelRun 零调用** — `remoteClient.ts:259` 全仓库无调用点：用户无法取消远端 run，AbortSignal 未贯通到 fetch/reader，应用退出时在途 run 成孤儿（服务端继续执行计费）。
8. **幂等键用 Date.now()** — `composition.ts:4002` `turnKey: \`${Date.now()}\`` 非确定性，违背 `remoteClient.ts:72` 注释语义；契约 `makeStaffdeckRunKey`（`digitalEmployeeRemote.routes.ts:166-168`）成死代码。应改用消息 id。
9. **空 hash 毒化 syncState** — `knowledgeClient.ts:180` `readString(concept.hash)` 不滤空串，`knowledgeSyncState.ts:163` `setEmployee` 用 `parse` 对整条员工状态抛错 → 该员工每轮同步静默失败且旧记录被拒写。修复：client 侧过滤空 hash，或 state 侧 sanitize 降级。
10. **knowledgeProvisioning RMW 丢配置** — `knowledgeProvisioning.ts:137` `setKnowledgeConfigs([...existing, config])` 无锁，两个员工并发 provision 时后写覆盖先写。
11. **knowledgeToolServer callTool 未过 schema** — `knowledgeToolServer.ts:86` 直接 `(parameters as {query?: string})?.query?.trim()`，query 非字符串时抛 TypeError；SearchArgsSchema 仅用于 tools/list。
