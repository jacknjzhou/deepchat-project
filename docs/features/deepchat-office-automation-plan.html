1 项目现状分析

1.1 项目定位

DeepChat 是一款开源、本地优先的 AI Agent 桌面客户端（v1.2.4），基于 Apache 2.0 协议。项目将模型、工具与 Agent Runtime 统一在 Electron 桌面应用中，支持多模型聊天、MCP 工具调用、ACP Agent 集成、Skills 系统、远程控制和定时任务。

用户仓库 jacknjzhou/deepchat-project 是上游 ThinkInAIXYZ/deepchat 的 fork，用于个人定制和二次开发。本地工作副本位于 D:\sync-workspace\traework\tools-market-project\deepchat-project。

1.3 Agent 执行架构

DeepChat 通过 AgentManager 统一管理两套独立的 Agent 后端：

Session / TurnCoordinator
↓
AgentManager
↓ ↓
DeepChat Backend
ACP Backend
↓
DeepChatLoopEngine
↓
processStream()
↓ ↓ ↓
ToolCatalogPort
ToolExecutionPort
ToolPermissionReviewer
↓
MCP Servers
Agent Tools
Skills
Plugins

执行主链路为：TurnCoordinator → DeepChatLoopRunner → processStream() → DeepChatLoopEngine.run()。引擎在 provider round 和 tool batch 之间循环，每次循环中 LLM 生成回复或工具调用，工具调用经权限审查后执行，结果回传给 LLM 继续推理，直到终端条件满足。

2 办公自动化需求分析

2.1 需求拆解

需求域核心场景关键能力现有基础扩展程度
报销 发票识别 → 报销单填写 → 审批提交 → 状态追踪 发票识别（视觉模型）、表单填充、审批流提交、状态查询 视觉模型 + 飞书审批 + 文件工具 中等扩展
发票识别 发票/收据 → 结构化数据提取 → 校验确认 视觉模型结构化提取、字段校验、多票据批量处理 多模态视觉模型通道 + Skill 机制 轻量扩展
流程提交 审批流发起 → 多级审批 → 结果通知 → 归档 审批 API 调用、流程状态管理、通知投递 飞书审批 + Scheduler + 权限系统 中等扩展
智能搜索 报销政策查询 → 开票方核验 → 流程模板搜索 网页搜索、结果摘要与引用 Bocha/Brave 内置搜索先例（in-memory 机制） 轻量扩展

2.2 能力差距分析

核心发现：DeepChat 已具备办公自动化所需的底层能力（多模态视觉模型、飞书集成、文档处理、定时任务、权限审批、内置搜索服务机制），但缺少面向具体办公场景的编排层——即将这些原子能力组合成完整业务流程的 MCP 工具和 Skill。
能力域已有能力缺失能力扩展策略
发票/票据识别 多模态图片附件、视觉模型通道 发票字段结构化提取模板（金额、税号、日期、商品明细）、字段校验规则、多票据批量处理 编写 invoice-recognition Skill，视觉模型按模板结构化提取（不建独立 OCR Server）
智能搜索 Bocha/Brave 内置搜索（in-memory 先例）；百度千帆 provider（用户已配置凭证） 百度搜索工具服务 新增 baiduSearchServer 核心 in-memory 服务，对接千帆 AI Search API（web_search），凭证复用千帆 provider 的 API Key
报销流程 飞书多维表格、审批 API、文件工具 报销单自动填充、审批流映射、报销记录管理 新建报销管理 MCP Server + Skill
流程提交 飞书审批 API、权限系统、通知投递 流程定义注册、多级审批编排、流程状态追踪、审批回调处理 新建流程管理 MCP Server + Skill
文档分类归档 文件工具、docx/pdf Skill 文档自动分类、归档规则、知识库索引 新建文档管理 MCP Server + Skill
定时自动化 Scheduler Cron 系统 报销提醒、审批催办、定期报表生成 编写 Cron 任务模板 Skill

3 扩展方案设计

3.1 整体架构

采用 Plugin + In-Memory MCP Server + Skill 三层扩展策略，最大化复用现有基础设施：

↓

发票识别（视觉模型提取）

↓

↓

外部服务
设计原则：
  • 不侵入核心引擎 - 不修改 DeepChatLoopEngine 和 processStream()。唯一核心变更是新增百度搜索 in-memory server，经 builder.ts / settings.ts 既有标准扩展点注册（与 Bocha/Brave 同机制）
  • 复用现有能力 - 发票识别不建独立 OCR Server，由 invoice-recognition Skill 指导视觉模型完成结构化提取；飞书、文件工具、Scheduler 作为依赖注入，不重复造轮子
  • 权限可控 - 所有写操作经过 ToolPermissionBroker 审批，关键操作需用户确认
  • 渐进式扩展 - 按 Phase 分阶段交付，每个 Phase 独立可用
发票识别改为 Skill 的设计动机：视觉模型直接理解发票版面与字段语义，准确率优于「OCR 文字 + 正则规则」管线；免去独立 OCR 进程、解析规则库的维护成本；Skill 模板（字段定义 + 校验规则 + 提示词）可持续调优且随插件热更新。

3.3 MCP 工具设计

A. 百度搜索内置服务 (baiduSearch · 核心 in-memory)

实现为 src/main/mcp/inMemoryServers/baiduSearchServer.ts，仿 bochaSearchServer 机制注册（builder.ts + settings.ts DEFAULT_INMEMORY_SERVERS）。对接百度千帆 AI Search API（智能搜索生成服务，qianfan.baidubce.com/v2/ai_search/web_search），凭证复用百度千帆 provider——同一 API Key，无需单独开通其他百度搜索服务。属 DeepChat 内置工具服务，所有会话可用；办公场景用于报销政策查询、开票方信息核验、流程模板搜索。发票识别不在本层——由 invoice-recognition Skill 承担（见 3.4）。

工具名输入输出说明
baidu_web_search query (关键词) / count (top_k, 1-50) / freshness (时间范围: 不限/一年内/一月内/一周内/一天内) / siteFilter (可选站点过滤) 结果列表 (标题/URL/摘要/站点/日期)，application/deepchat-webpage resource 块 调用千帆 AI Search web_search 接口（search_source: baidu_search_v2），结果结构与 Bocha 同构；readOnlyHint 只读放行

注：千帆 AI Search 为统一接口（无独立资讯端点），资讯/垂直过滤经 resource_type_filter / search_filter 参数实现，按官方文档能力开放。另有 /v2/ai_search/chat/completions（AI 搜索问答，模型参与总结）不在本方案范围。

B. 报销管理 Server (office-reimbursement-server)

工具名输入输出说明
create_reimbursement 报销类型/金额/事由/附件路径/发票数据 报销单 ID + 预览 自动填充报销单，关联发票数据
submit_reimbursement 报销单 ID + 审批人 审批实例 ID + 状态 提交到飞书审批流
track_reimbursement 报销单 ID / 审批实例 ID 当前审批状态/节点/下一步 查询审批进度
list_reimbursements 时间范围/状态/类型 报销单列表 查询历史报销记录
export_reimbursement 报销单 ID + 格式 导出文件路径 导出为 Excel/PDF
reimburse_summary 时间范围/部门 统计摘要 JSON 报销统计分析

C. 流程提交 Server (office-workflow-server)

工具名输入输出说明
search_workflow_definitions 关键词 可用审批流程定义列表 搜索飞书审批定义
get_workflow_definition 定义 ID 表单字段/审批节点 查看流程定义详情
submit_workflow 定义 ID + 表单数据 + 审批人 审批实例 ID 发起审批流程
track_workflow 审批实例 ID 状态/当前节点/审批记录 追踪流程进度
approve_workflow 审批实例 ID + 审批意见 + 通过/拒绝 操作结果 处理待审批任务
list_pending_approvals 用户 ID (可选) 待审批任务列表 查询待办审批

register_workflow_callback 审批实例 ID + 回调配置 回调注册结果 注册审批状态变更通知

3.4 Skill 设计

核心新增
invoice-recognition

引导 Agent 用视觉模型识别发票（本方案识别能力的核心）

  • 接收用户发票图片/PDF（会话附件或文件路径）
  • 视觉模型按字段模板结构化提取（类型/代码/号码/日期/金额/税额/购买方/销售方/明细）
  • 内置校验规则：价税合计 = 金额 + 税额、号码位数、日期格式
  • 低置信度或校验失败 → 标注问题字段请用户核对
  • 输出严格 JSON（供 create_reimbursement 等下游使用）
  • 可选 baidu_web_search 核验开票方/查询报销政策
  • 多张发票逐张提取后汇总
office-reimbursement

引导 Agent 完成报销全流程

  • 接收用户发票图片/PDF
  • 按 invoice-recognition 流程视觉提取数据
  • 校验发票信息完整性
  • 调用 create_reimbursement 创建报销单
  • 用户确认后 submit_reimbursement
  • 调用 track_reimbursement 追踪
process-submission

引导 Agent 提交审批流程

  • 理解用户审批需求
  • 调用 search_workflow_definitions
  • 获取流程表单定义
  • 辅助用户填写表单
  • 用户确认后提交
  • 追踪并通知结果
office-scheduler

引导 Agent 配置定时办公任务

  • 报销提醒 Cron 任务模板
  • 审批催办定时任务模板
  • 月度报表生成任务模板
  • 调用 cronjob Agent Tool 创建
  • 配置结果投递 (delivery targets)

3.6 典型工作流

场景一：发票报销

用户: "帮我报销这3张发票 [图片1.jpg, 图片2.jpg, 发票.pdf]"

Agent (invoice-recognition → office-reimbursement Skill):
  1. 视觉模型提取 图片1.jpg → {类型: 增值税专用发票, 代码: 1100243170, 号码: 48275836,
       开票日期: 2026-09-08, 金额: 1280.00, 税额: 128.00, 价税合计: 1408.00, ...}
     校验: 1280.00 + 128.00 = 1408.00 ✓
  2. 视觉模型提取 图片2.jpg → {类型: 增值税普通发票, 金额: 560.00, 税额: 56.00, ...} ✓
  3. 视觉模型提取 发票.pdf → {类型: 电子发票, 金额: 3200.00, 税额: 320.00, ...} ✓
  4. 汇总: 总金额 5040.00, 总税额 504.00 → [用户确认提取结果]
  5. 可选: baidu_web_search("差旅费 报销标准") → 辅助确定报销类型
  6. create_reimbursement({
       type: "差旅费",
       totalAmount: 5040.00,
       items: [...],
       attachments: ["图片1.jpg", "图片2.jpg", "发票.pdf"]
     }) → 报销单 ID: RMB-2026-001
  7. [用户确认] → submit_reimbursement(RMB-2026-001, 审批人: "张三")
  8. → 审批实例 ID: FA-20260912-001, 状态: 审批中
  9. track_reimbursement(FA-20260912-001) → 当前节点: 部门负责人审批

场景二：定期报销提醒

用户: "每月25号提醒我提交本月报销"

Agent (office-scheduler Skill):
  1. cronjob create({
       name: "月度报销提醒",
       cronExpr: "0 9 25 * *",
       timezone: "Asia/Shanghai",
       taskPrompt: "查询本月已识别但未提交的发票，
                    汇总金额后提醒用户提交报销",
       delivery: {
         targets: [{ type: "im", chatId: "用户单聊" }]
       }
     })
  2. → 任务已创建，下次运行: 2026-09-25 09:00

场景三：审批流程提交

用户: "帮我提交一个请假流程，请假3天，事由是家中有事"

Agent (process-submission Skill):
  1. search_workflow_definitions("请假") → [{id: "leave-001", name: "请假审批流程"}]
  2. get_workflow_definition("leave-001") → {
       formFields: [
         {key: "leave_type", label: "请假类型", type: "select"},
         {key: "start_date", label: "开始日期", type: "date"},
         {key: "days", label: "请假天数", type: "number"},
         {key: "reason", label: "事由", type: "text"}
       ],
       approvers: ["直属上级", "HR"]
     }
  3. 辅助用户填充表单:
     {leave_type: "事假", start_date: "2026-09-15", days: 3, reason: "家中有事"}
  4. [用户确认] → submit_workflow("leave-001", formData, approvers)
  5. → 审批实例 ID: WF-20260912-003
  6. track_workflow(WF-20260912-003) → 状态: 直属上级审批中

4.1 阶段划分

Phase 1: 基础设施搭建 + 百度搜索内置服务 预计 1-2 周

4.2 关键技术决策

决策点方案理由
MCP Server 实现方式 独立 Node.js stdio 进程（参考飞书插件） 进程隔离、可独立调试、与主进程解耦
发票识别方式 invoice-recognition Skill + 视觉模型结构化提取 视觉模型直接理解发票版面与字段语义，准确率优于 OCR+正则；免去独立 OCR 进程与解析规则维护；Skill 模板可持续调优（否决方案：独立 OCR Server / exec tesseract）
百度搜索集成 核心 in-memory MCP Server，对接千帆 AI Search API（web_search） 与 Bocha/Brave 同机制注册（builder.ts + settings.ts DEFAULT_INMEMORY_SERVERS）；凭证复用百度千帆 provider 的 API Key（同一凭证体系，无需单独申请搜索 Key）；作为内置工具服务供全部会话使用，独立于办公插件
飞书审批集成 复用已有 Feishu 插件 + lark-mcp preset 不重复实现 API 调用，通过 DeepLink 或 MCP 配置启用
报销数据存储 飞书多维表格（主存储） + 本地 SQLite 缓存 利用飞书已有插件能力，本地缓存支持离线查看
发票结构化策略 Skill 内置字段模板 + JSON Schema 约束 + 校验规则 视觉模型按模板输出严格 JSON，校验规则拦截算术/格式错误；模板随 Skill 热更新
工具权限默认值 只读 allow / 写操作 ask 平衡效率和安全，防止误操作

4.3 风险与对策

风险影响对策
中 视觉模型提取质量不稳定 发票字段提取错误，影响报销准确性 1) 提取结果用户确认环节 2) 字段校验规则（价税合计=金额+税额等）拦截算术错误 3) Skill 模板持续调优 4) 可切换更强视觉模型
高 飞书审批 API 权限不足 无法搜索/发起/查询审批流程 确保飞书 App 配置了审批相关权限域（approval:approval:readonly, approval:instance:create 等）
中 千帆 AI Search 配额与限流 web_search 接口有免费日调用上限（约 50 次/日），超出或限流时搜索工具失败 凭证复用千帆 provider（同一 Key 计费）；保留 Bocha/Brave 作为备选搜索服务；API Key 缺失时服务置灰并提示；错误经 MCP isError 通道返回由 Agent 自行降级
中 视觉模型未配置 发票识别功能不可用 Skill 检测视觉能力缺失时引导用户配置 defaultVisionModel 或切换多模态模型；本地 OcrRuntimeService 可作纯文字兜底
中 发票格式多样性 不同地区/行业的发票格式差异大 视觉模型天然适应多种版式（无需逐票种写规则）；第一阶段聚焦增值税发票（最常见），后续扩展其他票种
中 审批流程定义变化 飞书审批定义修改后工具失效 采用动态搜索定义而非硬编码 ID
低 性能（批量视觉提取耗时） 大量发票处理时响应慢 逐张提取即时反馈 + Scheduler 异步批量执行

5.2 百度搜索 In-Memory Server 骨架 (baiduSearchServer.ts)

// src/main/mcp/inMemoryServers/baiduSearchServer.ts
// 模式完全对齐 bochaSearchServer.ts：env 注入 apiKey + zod + toDeepChatJsonSchema
// 对接百度千帆 AI Search API（web_search），API Key 复用百度千帆 provider 的凭证
import { Server, Transport } from '@modelcontextprotocol/server'
import type { CallToolResult, ContentBlock } from '@modelcontextprotocol/server'
import { z } from 'zod'
import { toDeepChatJsonSchema } from '@shared/lib/zodJsonSchema'
import axios from 'axios'

const BAIDU_AI_SEARCH_ENDPOINT = 'https://qianfan.baidubce.com/v2/ai_search/web_search'

// 千帆 search_recency_filter 取值（按官方文档核对）
const RECENCY_MAP = {
  noLimit: 'noLimit',
  oneYear: 'year',
  oneMonth: 'month',
  oneWeek: 'week',
  oneDay: 'day'
} as const

const BaiduWebSearchArgsSchema = z.object({
  query: z.string().describe('搜索关键词（必填）'),
  count: z.number().optional().default(10).describe('结果数量 top_k（1-50，默认 10）'),
  freshness: z
    .enum(['noLimit', 'oneYear', 'oneMonth', 'oneWeek', 'oneDay'])
    .optional()
    .default('noLimit')
    .describe('时间范围过滤，默认不限'),
  siteFilter: z.array(z.string()).optional().describe('可选站点过滤（域名列表）')
})

// 千帆 AI Search web_search 响应结构（按官方文档对接，以下为设计示意）
interface QianfanWebSearchResponse {
  id: string
  references?: Array<{
    title: string
    url: string
    content: string // 摘要片段
    siteName?: string
    publishDate?: string
  }>
  // 其余字段（如 finish_reason）按官方文档核对
}

export class BaiduSearchServer {
  private server: Server
  private apiKey: string

  constructor(env?: Record<string, unknown>) {
    // 凭证优先级：env 显式配置 > （可选增强）注入 provider 凭证服务读取千帆 provider Key
    const apiKey = String(env?.apiKey ?? '')
    if (!apiKey) {
      throw new Error('需要提供百度千帆 API Key（与千帆 provider 同一凭证）')
    }
    this.apiKey = apiKey

    this.server = new Server(
      { name: 'deepchat-inmemory/baidu-search-server', version: '0.1.0' },
      { capabilities: { tools: {} } }
    )
    this.setupRequestHandlers()
  }

  public startServer(transport: Transport): void {
    this.server.connect(transport)
  }

  private setupRequestHandlers(): void {
    this.server.setRequestHandler('tools/list', async () => ({
      tools: [
        {
          name: 'baidu_web_search',
          description:
            'Search the web with Baidu (Qianfan AI Search) and get results including titles, urls, summaries, site names and publication dates.',
          inputSchema: toDeepChatJsonSchema(BaiduWebSearchArgsSchema),
          annotations: {
            title: 'Baidu Web Search',
            readOnlyHint: true,
            openWorldHint: true
          }
        }
      ]
    }))

    this.server.setRequestHandler('tools/call', async (request): Promise<CallToolResult> => {
      try {
        const { name, arguments: args } = request.params
        switch (name) {
          case 'baidu_web_search': {
            const parsed = BaiduWebSearchArgsSchema.safeParse(args)
            if (!parsed.success) {
              throw new Error(`Invalid search parameters: ${parsed.error}`)
            }
            const { query, count, freshness, siteFilter } = parsed.data

            // 千帆 AI Search web_search 请求体（Bearer 认证，Key 与千帆 provider 同源）
            const response = await axios.post(
              BAIDU_AI_SEARCH_ENDPOINT,
              {
                messages: [{ content: query, role: 'user' }],
                search_source: 'baidu_search_v2',
                resource_type_filter: [{ type: 'web', top_k: count }],
                search_recency_filter: RECENCY_MAP[freshness],
                ...(siteFilter?.length ? { search_filter: { match: { site: siteFilter } } } : {})
              },
              {
                headers: {
                  Authorization: `Bearer ${this.apiKey}`,
                  'Content-Type': 'application/json'
                },
                timeout: 10000
              }
            )

            const searchResponse = response.data as QianfanWebSearchResponse
            const pages = searchResponse.references ?? []
            if (pages.length === 0) {
              return { content: [{ type: 'text', text: 'No results found.' }] }
            }

            // 结果映射为 deepchat-webpage resource 块（与 Bocha 同构）
            const results = pages.map((item, index): ContentBlock => ({
              type: 'resource',
              resource: {
                uri: item.url,
                mimeType: 'application/deepchat-webpage',
                text: JSON.stringify({
                  title: item.title,
                  url: item.url,
                  rank: index + 1,
                  content: item.content,
                  siteName: item.siteName,
                  publishedDate: item.publishDate
                })
              }
            }))

            const summary: ContentBlock = {
              type: 'text',
              text: `Found ${results.length} results for "${query}"`
            }
            return { content: [summary, ...results] }
          }
          default:
            throw new Error(`Unknown tool: ${name}`)
        }
      } catch (error) {
        // 错误处理与 bochaSearchServer 一致：axios 错误带状态码，经 isError 通道返回
        const message = error instanceof Error ? error.message : String(error)
        return { content: [{ type: 'text', text: `Error: ${message}` }], isError: true }
      }
    })
  }
}

5.3 发票识别 Skill (SKILL.md) 骨架

---
name: invoice-recognition
description: 识别发票并提取结构化信息。Use when the user provides invoice
  images/PDFs or asks to extract invoice fields (发票/收据/报销票据).
metadata:
  deepchatFeature: office-automation
---

# invoice-recognition

Guide the agent to extract structured invoice data using the vision model.
Do NOT attempt to parse invoices with regex or external OCR tools — the
vision model reads the invoice layout directly.

## When to Activate
- 用户附加发票图片/PDF，或提到 发票 / 收据 / 报销 / 提取发票信息
- office-reimbursement Skill 需要发票数据作为输入

## Prerequisites
- 当前模型具备视觉能力，或已配置 defaultVisionModel
- 若均不可用：引导用户配置视觉模型，或请用户改用文字描述（不要臆造字段）

## Required Loop
1. 获取发票文件：会话附件优先；用户仅提供路径时读取文件后经视觉通道分析
2. 视觉模型按 Extraction Template 提取字段，输出严格 JSON
3. 校验（不过则标注问题字段，请用户核对）：
   - 价税合计 = 金额 + 税额
   - 发票号码 8 位 / 发票代码 10-12 位
   - 开票日期格式 YYYY-MM-DD（或 YYYY年MM月DD日 归一化）
4. 向用户展示提取结果表格，等待确认或修正
5. 确认后输出最终 JSON（供 create_reimbursement 等下游工具使用）

## Extraction Template
{
  "invoiceType": "增值税专用发票 | 增值税普通发票 | 电子发票 | 收据 | 其他",
  "invoiceCode": "string | null",
  "invoiceNumber": "string | null",
  "issueDate": "YYYY-MM-DD",
  "buyer": { "name": "string", "taxId": "string | null" },
  "seller": { "name": "string", "taxId": "string | null" },
  "amount": "number (不含税, 两位小数)",
  "tax": "number",
  "totalAmount": "number (价税合计)",
  "items": [{ "name": "string", "qty": "number", "unitPrice": "number", "amount": "number" }],
  "uncertainFields": ["识别置信度低的字段名"]
}

## Important Notes
- 缺失字段填 null，禁止凭空补全
- 金额一律两位小数；不要对金额做四舍五入以外的加工
- 多张发票逐张提取、逐张校验，最后汇总总额与总税额
- 可选：baidu_web_search 核验销售方信息或查询报销政策（只读，自动放行）
- 提取结果必须经用户确认后才可进入 create_reimbursement 流程

6 总结

方案可行性评估
维度评估说明
技术可行性 高 底层能力已具备（视觉模型、飞书、文件、Scheduler、权限），发票识别走 Skill + 视觉模型零新增服务；百度搜索有 Bocha in-memory 成熟先例
架构合理性 高 不触及 DeepChatLoopEngine/processStream()；唯一核心变更为百度搜索 in-memory server（新文件 + 2 处单行注册），与 Bocha/Brave 同机制
实施复杂度 中 2 个插件 stdio Server + 1 个核心内置搜索 Server + 4 个 Skill（含 invoice-recognition），需要飞书 API 调试和视觉提取模板调优
预计工时 7-11 周 5 个 Phase（OCR Server 工作量移除，Skill + 百度服务工作量较小），可并行部分工作
风险等级 中 主要风险在视觉模型提取质量、百度 API 配额与飞书 API 权限，均有对策
核心结论：DeepChat 已具备办公自动化的全部底层能力。本方案两项关键设计：① 发票识别不建独立 OCR Server，由 invoice-recognition Skill 指导视觉模型完成结构化提取（字段模板 + 校验规则内聚于 SKILL.md，零新增服务）；② 新增百度搜索内置工具服务（baiduSearchServer，对接千帆 AI Search web_search 接口，凭证复用百度千帆 provider 的 API Key，仿 Bocha in-memory 机制经 builder.ts / settings.ts 各一行注册）。整体通过 Plugin + in-memory MCP Server + Skill 三层架构，在不触及 DeepChatLoopEngine / processStream() 的前提下实现报销管理、发票识别和流程提交三大功能域。建议按 Phase 1（含百度搜索服务）→ Phase 2（发票识别 Skill）顺序启动——Phase 2 可独立验证视觉提取质量，是后续报销/流程功能的数据基础。
