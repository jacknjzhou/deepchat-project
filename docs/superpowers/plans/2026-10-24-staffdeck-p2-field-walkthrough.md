## 0. 这三项为什么要单独走查

| 项 | CI 里做不了的原因 | 真机需要什么 |
|---|---|---|
| P2-2 MCP 真机路径 | 单测的 `serverManager` 是桩（`mcpRegistration.test.ts` 的 `startServer: vi.fn()`），真机的重连、工具注册表刷新、`loadTools` 之后的实际可调用性都不在覆盖范围内 | 一个能连上的 StaffDeck MCP 端点（`POST /api/v1/mcp/agents/{id}`）+ 有效 `mcp:invoke` scope |
| P2-3 向量召回 | 建库时 `addFile` 打桩，因为本机没有启用的 embedding provider | 一个**启用**且配好维度的 embedding 模型 |
| P2-4 追问链路 | `awaiting_input` 只在真实 LLM 走到 SOP 的 `expected_user_info` 收集步骤时才产生，本地 `model_configs` 为空时恒不出现 | 服务端配好可用模型 + 某个会追问的技能/SOP |

> **P2-4 已经修过一轮代码**（`9a4d4d69`：追问明细原来只在首轮写入，第二轮起恒为空）。那次修复的读取侧有单测，**写入侧在 `composition.ts` 里没有单测**——所以这项仍需走查，重点是多轮追问（§3 步骤 6），不是「有没有提示条」。

先做一次环境自检，三项都靠它判断能不能开跑。

### 0.1 环境自检（5 分钟）

在应用里逐项确认，任一项不满足就记下「跳过」，不要试图绕过：

| 检查 | 操作路径 | 通过判据 |
|---|---|---|
| 连接配置齐备 | 设置 → 数字员工服务 | 已启用、Base URL 有值、External User ID 非空、显示「已保存密钥」 |
| key 有 `mcp:invoke` | 同页「测试连接」 | 提示「连接成功」。若提示「key 缺少 MCP 调用权限」→ **P2-2 无法开跑**，先找服务端补 scope |
| 员工列表来自服务端 | 数字员工广场页 | 不显示降级横幅；员工卡片上有真实工具数（非 0） |
| 有可用的 embedding 模型 | 设置 → 模型服务 | 至少一个 provider 已启用，且其下有一个 `type = embedding` 的模型未被单独禁用 |
| 服务端配好模型 | 服务端管理端 | 该员工绑定的技能/SOP 能实际跑起来（不依赖 deepchat 就能在服务端问出话） |

> 判定「列表来自服务端」不能只看有没有数据：mock provider 也有数据（`MOCK_DIGITAL_EMPLOYEES`）。看页面上是否有降级提示，或看工具数——mock 数据的工具是固定几条。

### 0.2 证据采集位置（全程用得到）

出问题时要能拿到现场，先记住这四个位置：

| 证据 | 位置 | 用途 |
|---|---|---|
| 应用日志 | 设置 → 通用 → 日志 → 「打开日志目录」，文件在 `{userData}/logs/` | MCP 连接、DuckDB 初始化、知识同步的 console 输出 |
| 数字员工配置 | `{userData}/app-settings.json` → `digitalEmployee` 子树 | 绑定表、知识同步状态表、技能同步状态表 |
| MCP 注册 | `{userData}/mcp-settings.json` → `mcpServers` 里 `staffdeck-*` 开头的键 | 注册是否写成、URL 与 Bearer 是否正确 |
| 向量库 | `{userData}/app_db/KnowledgeBase/{id}` | `de-` 前缀的目录是否存在、体积是否非零 |

Windows 上 `{userData}` 是 `%APPDATA%/OfficeAgent`。macOS 上是 `~/Library/Application Support/OfficeAgent`。

> 关闭应用后再读 `app-settings.json` / `mcp-settings.json`：它们在运行时可能还没落盘。读之前先备份一份，改坏了能还原。

## 1. P2-2：MCP `startServer` 真机路径

**要验证的假设**：注册写进配置 + `startServer` 成功 + `loadTools` 刷新之后，模型真的能看到并调用 `staffdeck_*` 工具。

原审计的疑虑是「单测里 `serverManager` 是桩」。真机上要看的其实是三件不同的事，分开验证，失败时才能定位到底断在哪一环。

### 步骤 1：注册是否写对

1. 广场页选一个 `local` 员工，点「开始对话」（可带开场问题）
2. 等页面跳转到聊天页
3. 关闭应用，打开 `{userData}/mcp-settings.json`

| 判据 | 期望 |
|---|---|
| 存在一个 `staffdeck-<slug>-<8位摘要>` 的键 | 有 |
| 它的 `type` | `http` |
| 它的 `baseUrl` | `{BaseURL}/api/v1/mcp/agents/{employeeId}`，员工 id 部分做了 URL 编码 |
| 它的 `customHeaders.Authorization` | `Bearer <key>`，key 与设置页保存的一致 |
| 它的 `enabled` | `true` |

任一项不符 → 属于 `mcpRegistration.ts` 的组装问题，与 MCP 运行时无关，不必继续往下走。

> 员工 id 含 `/`、`:`、空格时，`baseUrl` 里应当是 `%2F` 这类编码形式。解码后必须与原 id 完全相同。

### 步骤 2：连接是否真的建立

1. 重新启动应用
2. 打开 设置 → MCP（或插件 → MCP）
3. 找到该 `staffdeck-*` server

| 判据 | 期望 | 不符时说明 |
|---|---|---|
| 状态 | 已连接 | 「连接中」超过 45 秒 → 见步骤 2 下方的软超时说明 |
| 工具数 | 与服务端该员工暴露的工具数一致 | 为 0 → 服务端 `tools/list` 返回空，查服务端侧员工工具绑定 |
| 错误信息 | 无 | 「401 / 403」→ key 或 scope 问题；「404」→ baseUrl 拼错；「ENOTFOUND / ECONNREFUSED」→ 网络或反代 |

**软超时必须单独说明**：MCP 客户端在 45 秒（`MCP_STARTUP_SOFT_TIMEOUT_MS`）后会放弃等待、把连接放到后台继续（返回 `soft-timeout-released`）。这时：
- `startServer` 不抛错，注册侧会记成 `started: true`——所以「测试连接成功」不代表此刻已连上
- 界面可能先显示「超时」再自己变成「已连接」
- **判据以「最终是否变成已连接 + 工具数是否非 0」为准**，不要用「点下去那一瞬间的状态」

> 这正是 P2-2 值得真机跑一遍的理由：桩测试里没有这个 45 秒的中间态。

### 步骤 3：工具是否真的进了模型可见列表

1. 回到聊天页，打开输入框旁的 MCP 指示器（或 设置 → MCP → 工具列表）
2. 确认该员工的 `staffdeck_*` 工具在列表中

| 判据 | 期望 |
|---|---|
| 工具名 | 以 `staffdeck_` 开头，名字与服务端一致 |
| 归属 server | 指向那个 `staffdeck-*` 键，不是别的 server |
| 是否与当前会话相关 | 当前会话绑定的这个员工有工具；**另一个不相关会话不应看到它们** |

最后一行是 P1-10（孤儿注册清理）的验收点，顺带验。若在无关会话里也看到了，说明清理没生效或存在同名残留，回去看 `mcpReconcile` 的启动扫描日志。

### 步骤 4：真的调一次

1. 在对话里提一个必须用工具才能回答的问题（不是「你好」这类）
2. 观察模型是否发起工具调用

| 判据 | 期望 | 不符时说明 |
|---|---|---|
| 模型发起了 `staffdeck_*` 调用 | 有 | 完全不调 → 工具虽在列表里但未被模型选中，换个更明确的问题再试；仍不调则看步骤 5 |
| 调用返回成功 | 是，且有实际业务数据 | 报错里带服务端 code → 记下 code，属服务端侧 |
| 回答引用了工具结果 | 是 | 工具通了但回答没用到 → 提示词问题，与 MCP 无关 |

### 步骤 5：负面路径（同样重要）

这三条比正向更容易暴露问题，别跳过：

| 场景 | 操作 | 期望 |
|---|---|---|
| key 失效 | 服务端把 key 停用，重启应用后开新会话 | 工具列表为空，对话本身仍可用；不应崩、不应卡在「连接中」 |
| 服务端不可达 | 断网或改错 Base URL 后重启 | 同上，且「测试连接」给出网络错误而非权限错误 |
| 清理生效 | 服务端删除/停用该员工，重启应用 | 该 `staffdeck-*` 注册被清掉（看 `mcp-settings.json`），工具不再出现在任何会话 |

第三条对应 `mcpReconcile.ts` 的启动扫描。若注册仍在，注意一个设计约束：**拿不到可信员工名单时会整轮跳过**（provider 降级 / 拉取失败），这是有意的——按假 id 清理会删光真实注册。所以先确认当时列表是「真的空的」还是「拉取失败的空的」。

## 2. P2-3：向量召回端到端

**要验证的假设**：同步下来的概念能被 `similarityQuery` 检到，并进入系统提示词的「参考资料」段。

P0-1 修的是「用错了 id」，但那次修复只在单测里验证过（`localKnowledgeBaseId` 的回传与使用）。真机要验证的是**索引里真的有向量、检索真的命中**。

### 步骤 1：确认 embedding 条件成立

1. 设置 → 模型服务，确认有启用的 embedding 模型
2. 该模型的 `dimensions` 能被探测到

| 判据 | 期望 | 不符时说明 |
|---|---|---|
| 存在启用的 embedding 模型 | 有 | 没有 → 跳过本节，先解决「无 embedding 模型」 |
| 探测到维度 | > 0 | 探测失败时建库会写 `dimensions = 0`，后续索引阶段会显式报错（不会静默返回空） |

> 写 0 而不是猜一个 1536 是刻意的：猜出来的维度会让检索永远返回空且不报错，比直接失败更难查。

### 步骤 2：触发一次同步并确认落盘

1. 选一个有知识的 `local` 员工，点「开始对话」（首轮会触发同步）
2. 等 1–3 分钟（下载限并发 3）
3. 关闭应用，检查三处

| 判据 | 位置 | 期望 |
|---|---|---|
| 状态表有记录 | `app-settings.json` → `digitalEmployee.knowledgeSync.{employeeId}` | 存在，`localKnowledgeBaseId` 为 `de-` 开头的值，`packages` 下有远端 `kb_*` 键 |
| 概念已记账 | 同上 → `packages.{kb}.concepts` | 概念条数 > 0，每条有 `hash` 与 `fileId` |
| `stale` 为假 | 同上 → `packages.{kb}.stale` | `false`。为 `true` 时看 `staleReason` 定位 |
| 向量库存在 | `{userData}/app_db/KnowledgeBase/de-{employeeId}/` | 目录存在，体积明显大于空库 |
| 概念正文落盘 | `{userData}/digital-employee-knowledge/de-{employeeId}/` | 有 `.md` 文件，内容与概念对得上 |

`staleReason` 的处置对照：

| 值 | 含义 | 下一步 |
|---|---|---|
| `NO_EMBEDDING_MODEL` | 没有可用的 embedding 模型 | 回步骤 1 |
| `HTTP_401` / `HTTP_403` | key 失效或 scope 不足 | 查设置页的测试连接 |
| `UNREACHABLE` | 连不上服务端 | 查网络与 Base URL |
| `PARTIAL` | 部分概念下载或索引失败 | 看应用日志里的下载失败记录 |

### 步骤 3：确认本地库 id 与远端库 id 不是同一个

这是 P0-1 的核心，必须在真机上亲眼确认一次：

| 判据 | 期望 |
|---|---|
| 状态表里的 `localKnowledgeBaseId` | `de-` 开头 |
| 状态表 `packages` 的键 | `kb_` 开头 |
| 两者 | **不相等**，且向量库目录名用的是前者 |

若维护者将来把两者统一了，这段要改写——但当前设计是分开的。

### 步骤 4：检索真的命中

1. 打开该员工的一个**新**会话，开场问题就问一个只有知识库里才有的具体问题（不要问泛泛的「你能做什么」）
2. 观察回答

| 判据 | 期望 | 不符时说明 |
|---|---|---|
| 回答包含知识库里的具体信息 | 是 | 回答泛泛而谈 → 没召回到，见下 |
| 应用日志无 `Knowledge config not found` | 无 | 出现即说明又用远端 id 去检索了，属 P0-1 回归 |
| 应用日志无 `Error during similarity query` | 无 | 有则看堆栈：embedding 调用失败 / 维度不匹配 / 库打不开 |

排查顺序（召回为空时按这个顺序，别跳）：

1. `similarityQuery` 是否被调用？→ 需要 `knowledgeBaseIds.length > 0` **且**有开场问题，两者缺一都不会检索
2. 返回值是空数组还是抛错被吞？→ 当前实现 `.catch(() => [])`，抛错与空结果在界面上长得一样，必须看日志
3. `fragmentsNumber`（默认 5）与 `topK` 是否把命中截掉了？→ 概念少时不明显，概念多时可能命中但在第 6 名开外
4. 概念正文是否真的是自然语言？→ 正文里若混进大段结构化 JSON，切块后会稀释检索命中率

### 步骤 5：增量同步

1. 服务端改一个概念的正文
2. 等一个同步周期（默认 1h，可在设置里临时调小）
3. 再问一次同一个问题

| 判据 | 期望 |
|---|---|
| 只有那一个概念的 `hash` 变了 | 是（看 `app-settings.json` 里的 `concepts`） |
| 未变的概念没有重新下载 | 是（`lastSyncAt` 更新但 `fileId` 不变） |
| 回答反映新内容 | 是 |

> 增量判据是 per-concept hash，不是 `configHash`。若发现每次都全量重拉，说明判据退化成了 `configHash`。

## 3. P2-4：追问链路

**要验证的假设**：`awaiting_input` 出现 → 提示条正确 → 用户回答后同会话续跑。

> **本节在第 6、7 步之前先看一句**：本轮已修掉一个缺陷——追问明细原来只在首轮生效，第二轮起 `remoteStatus` 恒返回 `null`（`9a4d4d69`）。所以如果你的环境里追问只发生在**首轮之后**，走查时必须专门验证第 6、7 步；只在首轮看到提示条**不足以**判定通过。

### 步骤 1：制造一次真实追问

需要一个会追问的技能/SOP（服务端 `expected_user_info` 收集步骤）。这类技能通常在信息不全时才追问，所以：

1. 用一个信息**故意不全**的请求（例如只说「帮我报销」而不给金额、事由）
2. 不要一次把话说全

| 判据 | 期望 | 不符时说明 |
|---|---|---|
| 该轮结束时出现追问提示条 | 有 | 不见提示条 → 先看步骤 2；从来没有过 → 服务端没走到追问步骤，换技能或补请求 |
| 提示条位置 | 输入框上方，amber 色边框 | 位置不对属于 UI 问题，与链路无关 |
| 提示条内容 | 有标题「需要补充信息」；有 `question_summary` 时显示它；有 `expected_fields` 时列出字段 | 只有标题没有明细 → 明细取不到，见步骤 2 |

### 步骤 2：确认明细来源正确

提示条的明细不来自事件，而是事件到达后**回查 `remoteStatus`**。

| 判据 | 期望 | 不符时说明 |
|---|---|---|
| 事件 `digitalEmployee.remoteRunUpdated` 的 `phase` | `awaiting_input` | 若为 `completed` → 服务端没产生 `awaiting_input`，不是客户端问题 |
| 事件里是否带明细 | **不带**（设计如此） | — |
| 回查 `digitalEmployee.remoteStatus` 的 `awaitingInput` | 非 null，含 `expected_fields` | 为 null → 见下方「已知失败点」 |

**已知失败点（本轮已修，走查时重点确认）**：`awaitingInput` 只从 `remoteRunOutcomes` 这一份存储读，写入方有两处——首轮由 bind/switch 路由写，之后每轮由 `remoteTurn.send` 写。修之前只有前者，所以第二轮起的提示条恒为空。走查时：
- 首轮就追问 → 通过不能说明什么
- **第二轮或之后才追问 → 提示条必须照样出现**，这才是本轮修复的验收点

### 步骤 3：提示条消失时机

| 场景 | 期望 |
|---|---|
| 用户发了下一条消息（即回答） | 用户消息发出后，提示条消失 |
| 那一轮结束时服务端没有再追问 | 提示条保持消失（不能被旧明细重新拉起） |
| 那一轮结束时又追问了（换了个字段问） | 提示条重新出现，内容换成新的 `expected_fields` |

第二条靠的是「每轮都写，含 null」。若出现「答完了提示条还挂着」，就是写入侧漏了 null。

### 步骤 4：续跑是否在同一远端会话

追问的回答就是一条普通消息，走 `remoteTurn.send`。

| 判据 | 期望 | 不符时说明 |
|---|---|---|
| 服务端侧看到的是同一个 session | 是 | 新建了 session → 绑定表丢了，查 `app-settings.json` 的 `remoteSessions` |
| 服务端侧看到的是新的 run | 是 | 复用旧 run → 幂等键算错 |
| 回答里带上了上一轮追问的上下文 | 是 | 服务端把追问当成新话题 → 该轮 `session_mode` 或 session id 不对 |

> 幂等键是 `deepchat:{sessionId}:{turnKey}`。同一轮重发不该产生第二个 run；不同轮必须不同。

### 步骤 5：负面路径

| 场景 | 操作 | 期望 |
|---|---|---|
| 追问期间断网 | 追问出现后断网，再回答 | 报传输错误；提示条状态不残留错乱；恢复网络后下一轮正常 |
| 追问期间切走会话 | 追问出现后切到别的会话再切回 | 提示条在该会话仍可见（明细按会话存，不是全局） |
| 追问后关闭应用再打开 | 追问出现后重启，回到该会话 | **提示条不再出现**（设计如此：追问明细不落库，重启后不恢复）。对话仍可继续 |
| `hybrid` 会话降级 | hybrid 会话在追问状态下远端失败 | 提示条清掉，界面提示「已自动切回本地执行」 |

第三条容易被误判成 bug，先明确预期：追问是瞬时的，重启后不补查旧 run——补查拿到的是与服务端现状不符的结论。

### 步骤 6：多轮追问（本轮修复的验收点）

这是最容易被漏掉、但恰好是修复核心的一步：

1. 制造一次追问（第 1 轮）
2. 只回答一部分字段 → 触发**第二次**追问
3. 再回答剩下的 → 结束

| 判据 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---|---|---|
| 提示条出现 | 必须 | **必须** | 不出现（已答完） |
| 明细内容 | 字段 A | 字段 B（新的） | — |
| `remoteStatus.awaitingInput` | 非 null | 非 null | null |

第 2 轮为空 → 修复没生效，检查 `composition.ts` 里 `remoteTurn.send` 之后那行 `remoteRunOutcomes.remember(...)` 是否还在。

### 步骤 7：混合场景（可选但值得）

| 场景 | 期望 |
|---|---|
| `hybrid` 会话从本地切到云端，首轮即追问 | 提示条出现（走 switch 路径写入） |
| 上一条之后继续第二轮的追问 | 提示条仍然出现（走 remoteTurn 路径写入） |

这两条覆盖了「两个写入方都工作」——只测其中一条会漏掉另一条。

## 5. 已知的「预期行为」与「真 bug」分界

走查时最容易把下面这些当成 bug。它们都是设计决定，先确认预期再判定：

| 现象 | 是 bug 吗 | 理由 |
|---|---|---|
| 追问提示条在重启后消失 | 不是 | 追问明细不落库；补查旧 run 会拿到与服务端现状不符的结论 |
| 知识库召回为空但没报错 | **可能是** | `.catch(() => [])` 会吞掉异常。必须看日志区分「真没命中」与「检索抛错」 |
| MCP 显示超时但稍后变已连接 | 不是 | 45 秒软超时后连接继续在后台进行 |
| 清理孤儿注册时「什么都没做」 | 不是 | 拿不到可信员工名单时整轮跳过，这是保护措施 |
| hybrid 在云端执行的轮次没有回流 | 不是 | 云端已归档，重报会产生两份且事后无法区分 |
| 没有追问明细，只有标题 | **是** | 明细应当从 `remoteStatus` 回查到 |
| 追问回答了但提示条还挂着 | **是** | 每轮都应写一次（含 null） |
| 第二轮追问不出现 | **是**（本轮已修） | 曾是写入方缺失，见 §3 步骤 6 |
| 无关会话里出现别的员工的 `staffdeck_*` 工具 | **是** | 孤儿注册未清理 |

## 6. 走查发现问题的记录方式

有问题时按这个格式记，便于直接转成修复项：

```
[P2-x 步骤 y] 现象：____
预期：____（引用本清单的哪条判据）
实际：____
证据：日志片段 / 配置文件片段 / 截图
判断：客户端 bug / 服务端行为 / 环境问题 / 清单描述有误
```

最后一类「清单描述有误」要单独标出来：走查清单本身也是文档，判据写错会让人反复去查一个不存在的问题。
